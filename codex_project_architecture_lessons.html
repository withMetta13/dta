Codex Complex Project Playbook

从一锅粥到协作操作系统

一个 Amazon Ads 自动优化项目踩过的三次架构坑，以及为什么现在的四角色 + 公共 MD 文档模式能让复杂项目稳住。

先给朋友一句话

这个项目真正学到的，不是“多开几个 Agent”，也不是“把流程写得更复杂”。真正的经验是：让 AI 高速循环，但必须把循环关在清晰边界里。

Agent 按职责分工，系统按契约分层，项目记忆写进 repo。 这句话就是三轮架构演化后留下来的核心方法论。

三套架构的演化

每一套架构都不是“错”，它们都解决了当时最痛的问题，也都暴露了下一层问题。

第一阶段

自由对话：快，但会混

你不断告诉 AI 需求，它马上改。早期推进很快，但数据读取、归因、诊断、建议和执行边界会被揉在一起。

  • 优点：启动快，反馈快。
  • 问题：后期无法追责。
  • 典型风险：AI 顺手把 L3 的证据连接做成 L6 的建议。
第二阶段

14 个 Session：边界稳，但人很累

L1-L7 每层一个实现对话，再配一个审计对话。系统边界保住了，但上下文被切碎，用户变成消息中转站。

  • 优点：层职责更清楚。
  • 问题：沟通成本爆炸。
  • 典型风险：每个 Agent 只知道局部事实，交界处反而容易出错。
第三阶段

四角色工作流：职责集中，契约保边界

系统仍按 L1-L7 分层，但 Agent 改为按职责分工：实现、审计、架构、复盘。状态写进 repo 文档，不靠长对话记忆。

  • 优点：AI 能自循环，用户不用人肉路由。
  • 问题：需要维护公共 MD 文档。
  • 适用：长期、大型、边界敏感项目。

图 1：为什么第一套会变成“一锅粥”

自由对话最大的问题不是 AI 不聪明，而是它太容易把局部合理的动作串成整体混乱。

图 2：为什么 14 个 Agent 会让用户变成人肉路由器

第二套架构把系统边界保住了，但把对话也按层切开。每个 Session 都知道局部，没人天然拥有完整上下文。

图 3：现在的四角色闭环

现在的系统不再按 L1-L7 拆 Agent，而是按职责拆 Agent。系统边界仍在代码和文档里，协作则通过角色和 workflow 运转。

公共 MD 文档分别在做什么

这些文档不是装饰。它们像项目的公共账本，让新对话、旧对话、实现者、审计者和架构者都从同一份事实出发。

AGENTS.md

项目最高层的行为规则。写项目目标、强制边界、安全原则、跨层修改规则和禁止事项。

  • 作用：告诉所有 Agent 什么绝对不能做。
  • 价值：防止 AI 因为“顺手”改出危险行为。

docs/PROJECT_OPERATING_SYSTEM.md

解释整个协作系统为什么这样组织。它定义四角色模式、硬契约与软协作的关系。

  • 作用：说明“Agent 按职责分工，系统按契约分层”。
  • 价值：防止未来又退回一层一个 Agent 的人肉路由模式。

docs/AGENT_WORKFLOW.md

具体交通规则。谁能改文件、谁只读审计、Elon 怎么发 Socrates、Socrates 怎么打回或交给 Da Vinci。

  • 作用：把自动转发和 quick audit 固化下来。
  • 价值：减少用户在多个线程之间复制粘贴。

docs/CURRENT_STATE.md

项目当前事实入口。记录主入口、系统边界、运行流程、配置主线、测试状态和已知风险。

  • 作用：新对话先读它，不靠旧记忆猜项目状态。
  • 价值：线程可以重开，但项目状态不会丢。

docs/ACTIVE_TASKS.md

当前任务登记和 Implementer 锁。记录谁在改、目标是什么、allowed files / forbidden files 是什么。

  • 作用：防止多个 Elon 同时改同一片系统。
  • 价值：把“能不能改这个文件”变成公开事实。

docs/TASK_HANDOFF.md

任务结束或中断后的交接记录。写实际修改、检查结果、未完成内容、风险和下一步建议。

  • 作用：让下一个 Agent 从交接记录接班。
  • 价值：不再靠用户复述“刚才做到哪了”。

图 4：这些 MD 文档如何维持契约秩序

公共文档把“项目事实”和“协作规则”从对话里拿出来，放到所有角色都必须读取的地方。

为什么现在这套是当前项目的“最优”

它不是所有项目的宇宙最优，而是这种长期、复杂、边界敏感项目的局部最优。

问题 旧架构怎么失败 现在怎么解决
AI 把系统改成一锅粥 自由对话里，AI 会自然跨层“顺手做”。 L1-L7 边界写进契约、schema、测试、allowed files / forbidden files。
用户变成人肉路由器 14 个 Session 需要用户手工转述。 Elon、Socrates、Da Vinci 通过 workflow 自动转发。
长对话污染判断 旧对话记忆越长，越容易引用过时事实。 新任务必须先读 CURRENT_STATE 和 ACTIVE_TASKS。
实现范围失控 AI 看到旁边有问题就顺手修。 每个实现任务先登记 allowed files / forbidden files。
审计变成空泛意见 审计容易变成风格建议或事后背书。 Socrates 必须独立读 diff、契约、测试结果，并区分 Blocking / Non-blocking。
关键理解：现在这套架构不是为了让流程看起来专业，而是为了让“谁能改什么、错了找哪层、下一步由谁判断”都变成公开事实。

这套系统如何稳步运行

1. 任务开始：先看公共事实

任何新任务都先读 AGENTS.md、CURRENT_STATE.md、ACTIVE_TASKS.md、AGENT_WORKFLOW.md。

这一步防止新线程靠旧印象工作。

2. 实现前：锁定范围

Elon 在 ACTIVE_TASKS.md 登记目标、责任层、allowed files、forbidden files、预期检查。

这一步防止“顺手改上游、顺手改下游”。

3. 实现后：留下交接

Elon 在 TASK_HANDOFF.md 写实际修改、检查结果、未完成内容、风险和下一步。

这一步让换线程不等于丢上下文。

4. 审计时：按证据判断

Socrates 不以 Elon 总结为事实，而是独立读项目状态、契约、diff、测试结果。

这一步防止审计变成“听实现者讲故事”。

5. 无 Blocking：交给架构判断

Socrates 无 Blocking 后把摘要交给 Da Vinci。Da Vinci 判断当前任务结束、下一步主线和任务大小。

这一步让实现闭环回到方向判断。

6. 两轮不收敛：停止互踢

如果同一任务两轮 Blocking 仍不收敛，停止 Elon/Socrates loop，交给 Da Vinci 重拆任务。

这一步防止 AI 在错误任务定义里空转。

给未来更大项目的优化方向

用 Skill 一键安装协作底盘

不要每次手工复制四套提示词。用 $project-os-bootstrap 初始化四角色 workflow 和公共 MD 文档。

Da Vinci 先做项目适配

不要硬套 Amazon Ads 的 L1-L7。每个项目先识别自己的模块、边界、高风险区和 Blocking 标准。

任务默认大一点，必要时再拆小

Da Vinci 应布置阶段级、可闭环的大任务，避免每个细枝末节都审计一次。只有高风险、边界不清、两轮 Blocking 不收敛时才拆小。

更大项目可以并行，但必须有文件边界

可以多 Implementer，但必须写清每个 Implementer 的 allowed files、forbidden files 和冲突处理方式。

审计分级

小任务 quick audit，阶段性交付 formal audit，涉及生产、客户、财务、真实执行时加强审计。

定期换线程，不丢记忆

长对话会污染判断。线程可以换，但公共 MD 文档不能丢；新线程从 repo 重新接管。

可以直接讲给朋友的版本

我一开始以为用 Codex 做复杂项目，就是不断跟它讲需求，让它改。后来发现这样很快，但数据、逻辑、归因会混在一起，后面错了根本查不出错在哪。

然后我把系统拆成很多层，每层一个 Agent，每层一个审计。边界是保住了，但我自己变成 14 个对话之间的人肉路由器，累到不行。

最后我发现，正确做法不是“每层一个 Agent”，而是“系统按契约分层，Agent 按职责分工”。实现、审计、架构、复盘分开；项目记忆写进 repo；Agent 之间按 workflow 自动转发。这样 AI 可以自己形成闭环，但不会把复杂项目改成一锅粥。

最后的判断力

这套架构不是为了崇拜流程。它只做一件事：让复杂项目的错误更容易被定位，让人的注意力从“转述消息”回到“判断方向”。

什么时候不要用满配？ 小脚本、小页面、一次性分析，不要一上来四角色全开。任务越小，流程越轻；风险越高，边界越强；上下文越长，记忆越要写进 repo。
